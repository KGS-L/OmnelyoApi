Le paradigme en une phrase

Un monolithe modulaire livré en une seule image conteneur exécutant quatre processus (api, worker, bot, migrate) — PostgreSQL est l'unique source de vérité, Redis n'est qu'un accélérateur transitoire, et tout travail long passe par une file de jobs durable détenue par la base (bails, heartbeats, reprise).

Pipeline vidéo : INGEST → PROCESS → RENDER → PUBLISH — chaque étape est un job PostgreSQL, enchaînée par le client (l'API est l'orchestrateur).

Les dix invariants

AD-1

PostgreSQL, unique source de vérité

Tout état métier en base via Alembic ; Redis ne stocke que du transitoire TTL ; aucune seconde persistance.

AD-2

Redis : requis pour l'auth, best-effort ailleurs

OTP / OAuth / liaison Telegram le requièrent ; rate-limit fail-open, wakeup dégradé en polling. Toute nouvelle clé Redis déclare son mode de dégradation.

AD-3

Isolation multi-tenant par filtre explicite

Accès via dépendance de membership ; chaque requête répète workspace_id == ; workspace étranger ⇒ 404 ; clés R2 revérifiées.

AD-4

File durable : un seul point de passage

Claiming exclusif par claim_next_job (FOR UPDATE SKIP LOCKED) ; toutes les transitions de statut passent par workers/job_state.py sous verrou de ligne.

AD-5

Dead-letter terminal

Après épuisement des tentatives, FAILED est permanent ; annulation uniquement depuis QUEUED ; récupération = nouveau job.

AD-6

Enchaînement piloté par le client

Aucun handler n'enfile l'étape suivante ; au plus un job actif par (vidéo, étape) et par publication — pas de doublon, pas de double débit de crédit.

AD-7

Argent : prix serveur, ledger append-only

Prix uniquement de provider_price_mappings ; cycle reserve/capture/release ; idempotence par contrainte unique ; entitlements à rédacteur unique ; webhooks vérifiés avant fulfilment.

AD-8

Un seul chemin de connexion sociale

Contrat SocialPublisher + registre ; tokens uniquement dans SocialConnection chiffrés Fernet ; l'ancien OAuth du bot (Flask :8420, tokens fichier) est voué à disparaître.

AD-9

Configuration unique

api/config.py (pydantic-settings, validateurs prod) est l'unique source ; le config.py racine est gelé — sa retraite est un chantier prioritaire (crash latent en prod read-only).

AD-10

Langue utilisateur : français

Toute chaîne visible de l'utilisateur est en français — API, bot, copy. (Docs FR, commits EN conventionnels.)

Dette assumée & chantiers à venir

  • Unification de la configuration (AD-9) — retirer le config.py racine ; corrige au passage le crash latent des conteneurs read-only en production.
  • Retraite de l'OAuth legacy du bot (AD-8) — serveur Flask :8420, core/youtube_auth.py, core/youtube_uploader.py, volumes bot.
  • Déduplication à l'enqueue — garantir mécaniquement « un job actif par (vidéo, étape) » sur POST /jobs (l'invariant AD-6 est posé, l'implémentation reste à faire).
  • Propriétaire du dispatch programmé — qui convertit scheduled_at en job PUBLISH ; à décider avant tout épique « calendrier ».
  • Fenêtre de double publication PUBLISH — pas de clé d'idempotence fournisseur ; à fermer avant tout scale-out multi-worker.
  • Bloqué business — activation de la facturation (prix), expiration des crédits, rétention R2, routes partenaires.
  • Ops — métriques, alertes, sauvegardes testées ; montée Redis 8.x à planifier ; aligner Python CI/image.

Et ensuite ?

Le spine est le contrat de cohérence : toute nouvelle story ou tout nouvel épique doit s'y conformer (ou explicitement l'amender via bmad-correct-course).

Ordre recommandé : corriger AD-9 et AD-8 via bmad-build → adopter le spine en compagnon d'une spéc bmad-spec → découper en épics et stories bmad-create-epics-and-stories → planifier le sprint bmad-sprint-planning.
